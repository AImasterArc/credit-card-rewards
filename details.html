2. 資料模型

erDiagram CATEGORY ||--o{ RULE : "categoryId" CATEGORY ||--o{ TXN : "categoryId" CARD ||--o{ RULE : "cardId" CARD ||--o{ TXN : "cardId" TXN ||--o{ ALLOCATION : "內嵌快照" RULE ||--o{ ALLOCATION : "ruleId" CATEGORY { string id PK string name string color int sortOrder bool archived } CARD { string id PK string name string bank string last4 int statementDay string roundingMode bool archived } RULE { string id PK string cardId FK string categoryId FK float rate int capAmount string resetPeriod string validFrom string validTo string[] channels string note int priority bool enabled } TXN { string id PK string cardId FK string categoryId FK int amount string date string channel string note int reward } ALLOCATION { string ruleId int spend float reward }

設計決策

決策原因
類型是獨立資料表可擴增；規則以 categoryId 關聯。用到的類型只能封存，不能硬刪。
只支援「消費上限」依需求；capAmount = null 代表無上限。
只算現金回饋依需求；取消點數 / 哩程換算。
指定規則「取代」一般消費依需求；超過上限的部分才改用同卡「一般消費」規則，不疊加。
Transaction 內存 allocations 快照額度是「依序吃掉」的，要能 O(筆數) 算出每條規則已用額度，不必每次重跑規則。
金額用 JS number（整數元）回饋以 rate/100 乘；加總後才取整，避免逐筆累積誤差（+1e-9 防浮點）。
卡片永遠軟刪除（封存）保留歷史；只有「永久刪除」會連同交易刪除，需二次確認。

rules:      'id, cardId, categoryId'
txns:       'id, cardId, categoryId, date'

3. 帳單週期

「重置」不是刪資料，而是已用額度 = 只加總目前週期內的 allocations。結帳日一過，週期區間改變，額度自然回滿；歷史永遠保留。

flowchart TD A["輸入 statementDay, 參考日 ref"] --> B["thisStmt = clamp(本月, statementDay)"] B --> C{"ref ≤ thisStmt ?"} C -- 是 --> D["end = thisStmt"] C -- 否 --> E["end = clamp(下月, statementDay)"] D --> F["prevEnd = clamp(end 前一個月, statementDay)"] E --> F F --> G["start = prevEnd + 1 天"] G --> H["週期 = [start, end] 含頭尾"]
情境 (statementDay=15)參考日週期
結帳日前2026-10-1009-16 ~ 10-15
結帳日當天 → 算本期2026-10-1509-16 ~ 10-15
結帳日隔天 → 新週期2026-10-1610-16 ~ 11-15
statementDay=31, 2 月2026-02-1002-01 ~ 02-28（月底取代）
跨年 statementDay=52026-12-2012-06 ~ 2027-01-05

規則的 resetPeriod 另有 calendarMonth（每月 1 日重置），供活動以自然月計算的卡使用。

4. 回饋分配演算法 allocate()

輸入：金額、類型、卡片、所有規則、日期、該卡先前的交易。輸出：allocations[]、取整後 reward、未回饋金額。

flowchart TD S(["allocate(amount, category, card, date)"]) --> Neg{"amount < 0 ?"} Neg -- 是（退款） --> N1["取第一條符合規則
無則取一般消費規則"] N1 --> N2["spend = 負值, reward = amount×rate
→ 回補額度"] N2 --> End Neg -- 否 --> L1["designated = 該卡此類型
且 enabled、在有效期內
依 priority 排序"] L1 --> L2["fallback = 該卡「一般消費」規則
（類型本身為一般消費時為空）"] L2 --> Loop1{"left > 0 且還有指定規則?"} Loop1 -- 是 --> T1["take = min(left, 規則剩餘額度)"] T1 --> T2["記錄 {ruleId, spend:take, reward:take×rate}
left -= take"] T2 --> Loop1 Loop1 -- 否 --> Loop2{"left > 0 且還有一般規則?"} Loop2 -- 是 --> F1["同上，標記 usedFallback"] F1 --> Loop2 Loop2 -- 否 --> Sum["raw = Σ reward
reward = round/floor(raw)"] Sum --> End(["回傳 allocations, reward, unrewarded"])

範例：餐飲 3% 上限 1,000，一般 0.5%（本期已用餐飲 700）

刷 500 元（餐飲）
  ├─ 餐飲規則剩餘 300 → 300 × 3%   = 9.0
  └─ 超出 200 → 一般消費 200 × 0.5% = 1.0
reward = round(10.0) = 10
已用額度（usedSpend）= 規則週期內所有交易的 allocations.filter(ruleId).spend 之和。退款的 spend 為負，所以自然回補。

6. 寫入與重算

因為額度是依時間順序吃掉的，任何「新增 / 編輯 / 刪除交易」或「修改規則」都會影響之後的交易，所以必須重算。

sequenceDiagram participant UI participant DB as db.ts participant R as rewards.ts participant IDB as IndexedDB UI->>DB: saveTransaction(txn, previous?) DB->>IDB: txns.put(txn) DB->>DB: from = 同卡且舊日期較早 ? 舊日期 : 新日期 DB->>DB: recomputeCard(cardId, from) DB->>IDB: 讀 card / rules / txns DB->>R: reallocate(card, rules, txns, from) Note over R: 依 (date, createdAt) 排序
from 之前的交易視為已定案
之後逐筆 allocate() R-->>DB: 變動的交易 DB->>IDB: txns.bulkPut(changed) IDB-->>UI: useLiveQuery 觸發重繪 opt 換卡 DB->>DB: 另對舊卡 recomputeCard(舊日期) end
操作重算範圍
新增交易該卡從該交易日期起
編輯（改日期 / 金額 / 類型）該卡從 min(舊日期, 新日期) 起
編輯（換卡）新卡從新日期起 + 舊卡從舊日期起
刪除交易該卡從該交易日期起（讓後面的交易拿回額度）
儲存卡片 / 規則從所有規則「目前週期起點」中最早者起；歷史週期保留快照不動

13. 邊界案例

案例處理
結帳日 29–31clampDate 取當月最後一天。
結帳日當天消費算本期。
規則被改 / 刪儲存時重算目前週期之後；歷史週期不動。
規則有活動期間交易日在期間外該規則不生效（走一般消費）。
類型被規則使用只能封存；封存類型仍顯示於既有規則 / 交易。
卡片無「一般消費」規則超額部分 0% 回饋，UI 標示 @0%；卡片編輯頁提示建議新增。
退款負 spend 回補額度，回饋為負。
同日多筆以 createdAt 決定順序。
時區全部使用本地日期字串，不用 UTC timestamp。
換月顯示紀錄頁以消費日的自然月分組；與「帳單週期」是不同概念，兩者並存。

14. 已知限制

  • 以消費日歸屬週期；銀行實際以入帳日計，跨結帳日邊界可能差一期。
  • 無雲端同步；換機需用 JSON 備份。
  • 通路比對為字串包含，不支援 MCC 碼。
  • 回饋以規則 % 估算，不處理銀行端的排除項（需看規則筆記）。
  • Safari 對 PWA 儲存無硬性保證；請定期匯出備份。
